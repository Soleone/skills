# Pattern selection

Read at the anchor step, not on every feedback revision.

## Current status

**No bundled composition has been visually approved yet.** This is the Phase 1 contract, not a finished pattern library. The next step is one runnable form pilot with user review. Do not claim a screenshot, starter, or vetted pattern exists before it does.

## Selection order

1. Reuse the host's approved equivalent screen and its documented behavior.
2. Use a previously user-approved runnable reference whose source and visual preview are available and whose task fits.
3. If neither exists, compose a provisional reference from documented official shadcn components. Show it as a candidate, not a proven design.

A reference is an anchor, not a license to copy unrelated sections. Favor the user's task over resemblance to a fashionable product. Stay within explicitly approved registries and verify licensing before importing third-party blocks. A public screenshot is not permission to copy proprietary assets or source.

## First pilot: single-column task form

Use when a person completes one bounded submission without needing persistent side-by-side context.

- A task title, optional necessary context, related fields, and a clear primary action.
- Plain document flow by default. Add sections only for meaningful field groups, not visual variety.
- Use current shadcn form composition and validation APIs from its skill/docs. Do not freeze API examples here.
- Required/optional semantics, useful validation, preserved values after errors, and a clear outcome.
- Realistic short/long content, narrow-screen layout, and usable keyboard order.
- Only necessary secondary actions; explain destructive or irreversible consequences where relevant.
- No decorative progress stepper for a single step, unrelated sidebar, invented trust badges, or accompanying dashboard.

This is a provisional structural brief, not the implementation or visual approval. Confirm the pilot domain/task and preset/base before building a new starter. If the host already supplies them, do not ask again.

## Approving a reusable reference

After the user reviews the runnable pilot, record in the project's existing design document:

- Task and when this composition fits; when it does not.
- Exact source path/revision and launch command or route.
- A current visual preview path and the relevant viewport.
- Preset/base, dependency versions, and approved layout conventions.
- Supported interaction states and known mock boundaries.
- Approval status and explicit deviations from stock components, if any.
- Origin/license of imported assets or blocks.

Do not promote a changed reference automatically. Meaningful structural or visual changes need a new review; dependency updates need verification against the approved behavior and appearance.

## Grow from real needs

Possible later references: sectioned settings and list/detail workspace. These are not available templates yet. Add one only when the form pattern fails a real task and a reviewed implementation exists. Keep the index small; do not build a configurable universal page generator.
